# FINDINGS — Home Assistant token custody

Audit date: 2026-11-04. Method: shipped source read at pin + gold-standard live proof on our own instance (localhost, disposable). No third-party instance was touched; no live service was interacted with.

## The construction in one paragraph
Every credential that can act as a Home Assistant user — every refresh-token secret and every per-token JWT signing key, for every user — is stored in cleartext in a single file, `config/.storage/auth` (file mode 0600). Passwords in the neighbouring store are bcrypt-hashed; token secrets are not hashed at all, because validation is a direct string comparison against the stored value. Two of the three token classes are created with `expire_at = None` and never expire; the third expires only after 90 days *unused*, with the deadline slid forward on every use. Changing a password — by the user, by an admin, by Supervisor reset, or by CLI — rehashes the password record and revokes nothing; the only revocation paths are manual per-token deletion in the profile UI, an opt-in "sign out of all sessions" prompt offered *after* a self-service password change in the web frontend, user deletion, and user deactivation (the last two are impossible for the owner account, which is the primary account in most homes). The automatic-backup encryption password is likewise stored in plaintext, in `.storage/backup`, in the same directory that every backup archives — so one read of a live config directory yields the live tokens directly *and* the key that decrypts every exported automatic backup, each of which independently contains the same `.storage/auth`.

## FALLS rows, verbatim
- **F1 (C3/C10/C11 FALL):** The claim sentence is: "Your password is the key to your home, so choose a strong, unique one." The code fact: the keys to the home are the bearer tokens in `.storage/auth`; the password is one way to *mint* them, and changing it revokes none of them. Proven live (Phase 4): after a real password change (old password rejected with `invalid_auth`, new accepted), a refresh token copied from `.storage/auth` *before* the change still minted fresh access (HTTP 200, `/api/config` 200), and a long-lived access token minted before the change still authenticated (200).
- **F2 (C11 FALL, expiry half):** Long-lived access tokens are documented as valid for 10 years; their parent refresh tokens in fact have **no expiry at all** (`expire_at = None`, auth/__init__.py:507–509), and the WebSocket creation command accepts an arbitrary caller-supplied `lifespan` in days with no upper bound in core (components/auth/__init__.py:637–666); 3650 is only the frontend's hardcoded choice.
- **F3 (C8 bound crossing into FALL for the implied claim "encrypted backups protect their contents from someone who obtains the installation's files"):** The automatic-backup password is persisted in plaintext in `.storage/backup`; the code says so itself — components/backup/store.py:42: "The store persists the automatic backup password in plaintext."

## Per-class expiry / revocation matrix (plain sentences)
- **Normal refresh token** (browser/app logins): secret generated with `secrets.token_urlsafe(64)` — sound. Expires 90 days after *last use*; every access-token mint slides the deadline forward 90 days, so a token in use never expires. Revoked by: manual deletion (profile list, `auth/delete_refresh_token`, or RFC 7009 `/auth/revoke` with the string), the opt-in sign-out-all prompt after a self-service password change, user deletion, user deactivation, credential removal (only tokens bound to that credential). NOT revoked by any password change.
- **Long-lived access token** (scripts; a JWT backed by a dedicated refresh token): the JWT's lifetime is the caller-supplied lifespan in days — 3650 from the shipped UI, unbounded in the core API. Its parent refresh token never expires. The JWT string is not stored; the parent secret and signing key are, in cleartext. Revoked only by deleting the parent (profile list / WS / user deletion / deactivation / opt-in sign-out-all). NOT revoked by any password change — proven live.
- **System refresh token** (system users: Supervisor legacy, Home Assistant Cast with admin group, HTTP content user read-only): never expires. Supervisor's own tokens are now proactively removed at setup because Supervisor authenticates over a dedicated Unix socket — credited as sound. Cast's system token string is handed to the Cast flow. Revoked by user deletion of the system user or manual deletion.
- **Access token** (JWT, HS256, per-token key): 30 minutes by default (or the lifespan, for LLATs). Dies with its parent; parent deletion is enforced at validation because the signing key disappears with the record.
- **Webhook IDs** (not user tokens): `secrets.token_hex(32)` capability IDs, sound entropy; unauthenticated by design; `local_only` webhooks reject cloud/remote callers. They live in plaintext in `.storage/core.config_entries`, so a config read also yields every webhook capability URL.
- **Cloud (Nabu Casa) account tokens**: Cognito id/access/refresh tokens stored in cleartext JSON at `config/.cloud/production_auth.json` (mode 0600). A separate credential system from HA auth — but it shares the same directory, so the same single file-read takes it too.

## Backup answer
Backups **are encrypted by default**: per-agent `protected` defaults to True, and the cloud agent refuses unprotected backups outright ("Cloud backups must be protected"). Encryption is SecureTar (securetar==2026.10.0) over the inner folder tars. The automatic-backup password, however, is **stored in plaintext in `.storage/backup`** (the code comments this itself), and `.storage/auth` **does ride inside backups** — a settings backup contains the whole config folder, `.storage` included, and a restore resurrects the token state wholesale (the vendor's own docs instruct users to log in after restore with the password "as they were at the time the backup was taken"). Net: one read of a live config directory = the live tokens directly, plus the password that decrypts every automatic backup the user has ever exported; each decrypted backup independently contains the same token file. A backup archive *alone*, without the live directory, remains protected by its password — that part of the design holds.

## Nabu Casa remote answer
The remote-access path is better built than the token layer: TLS for the remote UI **terminates at the instance**, with an ACME certificate issued to the instance's own domain and the private key held locally; the SniTun relay routes by SNI and holds no HA session material, no HA token, and no TLS key (hass-nabucasa 2.8.1, remote.py — `_create_context` loads the local chain into the local aiohttp runner; `SniTunClientAioHttp` wraps that runner). Arriving through the tunnel still requires ordinary HA authentication, and `local_only` users are refused on cloud connections. A **cloud-account compromise yields control of the instance's remote registration/domain routing, cloudhooks, voice pipelines, cloud backups and subscription — and no HA token**: no code path in core's cloud component or hass-nabucasa mints HA auth tokens from cloud credentials. The join is on disk, not in protocol: the cloud account's Cognito refresh token sits in plaintext in the config directory (above), so the file read that takes the house also takes the cloud account.

## Live proof (Phase 4, summary)
On our own 2026.11.0 instance (localhost only): created owner user; minted a normal refresh token and a 3650-day LLAT (JWT exp−iat measured at exactly 315,360,000 s); copied `.storage/auth`; changed the password through the real WS command; verified the old password fails (`invalid_auth`) and the new one succeeds — and, from the copied material alone, (a) the copied refresh token still minted access (grant 200, `/api/` 200, `/api/config` 200) and (b) the pre-change 10-year LLAT still authenticated (200). Garbage token: 401. Only manual per-token deletion killed them (refresh grant → 400 `invalid_grant`; LLAT → 401). Full timestamped log: evidence/LOG.txt (box: /opt/muse/audits/ha/proof/LOG.txt).

## What is sound (credited at the same weight)
- All generation entropy: refresh secrets `secrets.token_urlsafe(64)`, JWT keys `secrets.token_hex(64)`, webhook IDs `secrets.token_hex(32)`.
- Passwords bcrypt-hashed (rounds=12); dummy-hash timing equalisation on unknown users.
- Per-token JWT signing keys (one token's key compromise signs nothing else); 30-minute default access tokens; 10-second validation leeway.
- Supervisor's migration off refresh tokens to socket authentication, with proactive removal of its legacy tokens at setup.
- Backup encryption default and the cloud agent's hard protection requirement; `.storage` files at mode 0600.
- The remote UI's end-to-end TLS termination at the instance.
- The frontend's opt-in sign-out-all prompt after a self-service password change (it exists and, if accepted, deletes all token types) — the bound is that it is opt-in, frontend-only, and not part of the password change itself.

## Failures, bounds, unread areas (stated plainly)
- The proof driver failed twice before the clean run (a shadowed import; a logging crash after the change-password command had been sent) — instance wiped and re-run; the aborted runs are disclosed in the Phase 4 note, and no claim rests on them.
- Not read: companion app (iOS/Android) source — mobile tokens are asserted only as consumers of the normal class via the standard OAuth flow; the Supervisor repository (tar assembly on HAOS is Supervisor-side; core-side inclusion of the config folder is docs-stated and restore-path-verified); the snitun library internals (the TLS termination point is proven from hass-nabucasa's construction, not from snitun's code); the securetar package's KDF (backup claim is about key *custody*, not cipher strength); HAOS ingress session mechanics.
- One code path not exercised live: the frontend's opt-in sign-out-all (code-proven in frontend 20261028.4 `ha-change-password-card.ts` + core defaults; the live proof exercised the backend change command exactly as the frontend's first step performs it).
- The vendor's security page explicitly excludes host-access attacks from its bounty scope and states all logged-in users are trusted as owners; this audit's claim is narrower and survives that posture: *stolen token material is durable* — it survives the one remediation users are taught to perform, in some classes forever, and the file that holds it (plus the backup password beside it) is the single most-copied artifact of the installation (backups, cloud sync, support bundles, migration archives).
