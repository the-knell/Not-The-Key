# Phase 3 — Nabu Casa remote trust path (core 2026.11.0 + hass-nabucasa 2.8.1)

- Remote UI = hass_nabucasa RemoteUI (remote.py): instance registers with the cloud API (cloud.instance.register returns domain, server, aliases); instance obtains its OWN ACME (Let's Encrypt) certificate for the instance domain locally (AcmeHandler; _create_context loads local fullchain+private key into the local aiohttp runner's SSL context); SniTunClientAioHttp (snitun) connects out to the assigned snitun server on 443 and the local aiohttp app is served through it. TLS therefore TERMINATES AT THE INSTANCE with a locally held key; the SniTun relay routes by SNI and holds no HA session material, no HA token, and no TLS private key. A relay/cloud transport compromise does not yield HA bearer tokens from the tunnel itself. (snitun library internals not read — bound; the termination point is proven by _create_context + SniTunClientAioHttp construction in remote.py:438-455.)
- Reaching the remote UI still requires normal HA authentication (the HA login flow runs over the tunnel; local_only users are refused on cloud connections — components/http/auth_util.py async_user_not_allowed_do_auth + helpers/network is_cloud_connection).
- What the CLOUD ACCOUNT itself holds, on disk: hass_nabucasa Cloud.update_token/_write_user_info (__init__.py:400-415, 695-713) writes {"id_token","access_token","refresh_token"} (Cognito) as plaintext JSON to <config>/.cloud/production_auth.json (path(): base_path=client.base_path=config_dir, CONFIG_DIR .cloud; file chmod 0600). So the same config-dir read that takes .storage/auth also takes the Nabu Casa account refresh token.
- What a cloud-account (Cognito) compromise yields against the token layer, from code: control of the cloud account = control of instance registration/remote domain routing, cloudhooks (vendor-relayed webhook endpoints), voice/Alexa/Google pipelines, cloud backup storage, and subscription — an attacker can point/re-register remote access and receive traffic destined for the instance domain (then faces the HA login page; password still required), and can call cloud APIs as the account. It does NOT directly yield any HA refresh/access token: no code path in core cloud or hass-nabucasa mints HA auth tokens from cloud credentials (account_link.py only links EXTERNAL services' OAuth into HA via the standard login flow; CloudRegisterAutoLoginView is a registration-time auto-login inside an already-authenticated local session). The HA token layer and the cloud account are separate credential systems that merely share a disk directory.
- Cloudhooks: cloud-relayed webhooks terminate in async_webhook_message -> the same webhook handler path; local_only webhooks are protected from cloud delivery by the webhook handler's is_cloud_connection check (components/webhook/__init__.py async_handle_webhook).
