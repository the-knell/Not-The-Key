# Phase 1 — Token lifecycle at core 2026.11.0 (all file:line in home-assistant/core @ 74cf5a49 unless noted)

## Classes and creation
- Three refresh-token types (auth/models.py): TOKEN_TYPE_NORMAL="normal", TOKEN_TYPE_SYSTEM="system", TOKEN_TYPE_LONG_LIVED_ACCESS_TOKEN="long_lived_access_token".
- RefreshToken fields (models.py:106-131): token = secrets.token_urlsafe(64) [~512 bits, sound]; jwt_key = secrets.token_hex(64) [512 bits, sound]; id = uuid4 hex. Access-token expiration default 30 min (auth/const.py ACCESS_TOKEN_EXPIRATION; REFRESH_TOKEN_EXPIRATION = 90 days in seconds).
- AuthManager.async_create_refresh_token (auth/__init__.py:487-551): token_type defaults system for system_generated users else normal; ONLY normal gets expire_at = now+90d (:507-509); system and long-lived get expire_at=None. LLAT requires client_name, one per client_name per user.
- Access token = JWT HS256 {iss: refresh_token.id, iat, exp: now+access_token_expiration} signed with that token's own jwt_key (auth/__init__.py async_create_access_token). Validation (async_validate_access_token): decode iss -> look up refresh token -> verify with its jwt_key, leeway 10s; rejects if user inactive. NOTE: validation does NOT check refresh_token.expire_at — expiry is enforced only by a scheduled sweeper (_async_remove_expired_refresh_tokens / _async_track_next_refresh_token_expiration) that removes expired tokens; between deadline and sweep an expired token's already-minted access token lives out its 30 min anyway.
- Sliding expiry: AuthStore.async_log_refresh_token_usage (auth_store.py:281-286), called from async_create_access_token: on every access-token mint, if expire_at set, expire_at = last_used_at + 90d. A used normal token never reaches its deadline. Docs' "expires when it has not been used for 90 days" is exactly this.

## Storage (the custody fact)
- AuthStore serialization (auth_store.py, _async_save data builder): refresh_tokens entries include "token": refresh_token.token AND "jwt_key": refresh_token.jwt_key in cleartext; store file is config/.storage/auth (helpers/storage.py: STORAGE_DIR=".storage", Store path = hass.config.path(".storage", key); auth store key "auth"). File written via Store with private=True (0600). Validation of a presented refresh token is hmac.compare_digest against the stored cleartext string (auth_store.py async_get_refresh_token_by_token).
- Passwords by contrast ARE hashed: provider Data.hash_password bcrypt rounds=12, base64 (auth/providers/homeassistant.py); credential records live in .storage/auth_provider.homeassistant. So in one directory: passwords bcrypt-hashed, every token secret + every JWT signing key plaintext.
- Consequence: read of .storage/auth = every user's every live refresh secret + the signing keys to mint/validate access JWTs offline for validity checks; refresh secrets are directly replayable at POST /auth/token (grant_type=refresh_token; handler checks refresh_token.client_id == client_id when client_id supplied — client_id is stored in the same file).

## Long-lived access tokens
- WS auth/long_lived_access_token (components/auth/__init__.py:637-666): schema requires lifespan:int (days) with NO upper bound in core; creates refresh token type long_lived_access_token with access_token_expiration=timedelta(days=lifespan), then mints ONE access token with that expiration and returns it; the JWT string itself is not stored (docs C6 true) — but its parent refresh token (never-expiring, expire_at=None) and jwt_key ARE stored, so the parent can mint fresh LLATs at will via async_create_access_token path? Bound: no shipped UI/WS command re-mints from an existing LLAT parent except /auth/token refresh grant using the parent refresh token STRING — which is only in .storage/auth, never shown to users. From file read, the parent string is available, so re-minting is available to a file reader.
- Frontend (20261028.4) ha-long-lived-access-token-dialog.ts:226 hardcodes lifespan: 3650 (10 years). Profile UI creation is the documented path.
- Killing a leaked LLAT string requires deleting its parent refresh token (profile Security list shows LLAT parents); password change does not (below).

## Revocation matrix (call-path proof)
- Manual single: WS auth/delete_refresh_token (components/auth/__init__.py:708-729) -> async_remove_refresh_token; also RFC7009 POST /auth/revoke (requires_auth=False, anyone holding the string can revoke it).
- Manual all (self): WS auth/delete_all_refresh_tokens (:731-769): defaults token_type=None (all types), delete_current_token=True.
- Profile "delete all" button in frontend ha-refresh-tokens-card.ts:324 calls deleteAllRefreshTokens(hass, "normal", false) — NORMAL TYPE ONLY, keeps current: the UI's own bulk action leaves LLAT parents and system tokens alive.
- User deletion: config/auth/delete -> AuthManager.async_remove_user (auth/__init__.py:360-376): removes ALL refresh tokens (+credentials). Owner cannot be deleted (guard in WS handler + manager raises for owner in remove/deactivate).
- User deactivation: async_update_user(is_active=False) -> async_deactivate_user (:419-425): store-deactivates + removes ALL refresh tokens. Owner cannot be deactivated.
- Credential removal: async_remove_credentials (:427-444): removes only refresh tokens bound to that credential.
- Expiry sweeper: removes tokens past expire_at (normal unused 90d only class that can be past).
- Supervisor setup (components/hassio/__init__.py ~474): removes any legacy refresh tokens of the supervisor system user — supervisor now authenticates over its Unix socket (components/http/auth.py async_authenticate_supervisor_unix_socket). Clean, credited.
- PASSWORD CHANGE — the negative result, all four entry points call ONLY the provider:
  1. Self WS config/auth_provider/homeassistant/change_password (components/config/auth_provider_homeassistant.py:131-168): verify step-up (current password) then provider.async_change_password -> Data.change_password (providers/homeassistant.py:180-196) = rehash + async_save. Full body read: no token call.
  2. Admin WS .../admin_change_password (:170-205): owner-only; same single call. Frontend dialog-admin-change-password.ts: only adminChangePassword + success state, no token action (and delete_all would act on the CALLER's tokens anyway, since WS delete_all operates on connection.user).
  3. Supervisor password reset POST /api/hassio_auth/password_reset (components/hassio/auth.py): supervisor-socket/IP-gated; same provider.async_change_password only.
  4. CLI homeassistant/scripts/auth.py change_password: provider.data.change_password only.
- FRONTEND OPT-IN (the one nuance beyond the survey): frontend ha-change-password-card.ts _changePassword: after changePassword succeeds, IF the card's refreshTokens prop is loaded, shows confirmation dialog ("sign out of all other sessions?", No = dismissText, Yes = confirmText); on Yes calls deleteAllRefreshTokens(hass) with no args -> core defaults delete ALL types incl. current. So shipped-UI self-service password change OFFERS full revocation as a separate opt-in step; it is not a property of the password change, defaults to a prompt the user can decline, and does not exist at all in the admin-change, supervisor-reset, or CLI paths. Docs C5 describes this prompt accurately.

## Other consumers/surfaces
- System users: Supervisor (above, socket auth now, no tokens), "Home Assistant Cast" system user (components/cast/home_assistant_cast.py): admin-group system user holding a SYSTEM refresh token whose .token string is handed to the Cast receiver flow; content user (components/http/auth.py async_setup_auth): read-only system user + system refresh token for signed-path/content URLs. System tokens: expire_at=None.
- Signed paths: WS auth/sign_path -> async_sign_path JWS (HS256, secret = content system token's jwt_key chain), default 30s expiry. Small, sound.
- Webhooks (components/webhook/__init__.py): async_generate_id = secrets.token_hex(32) (256-bit capability IDs, sound); /api/webhook/{id} is unauthenticated by design (capability URL); local_only webhooks reject non-local/cloud requests (with the 2023 SniTun CVE class addressed by is_cloud_connection check). Webhook IDs are NOT user tokens and are stored in each integration's config entries (plaintext, in .storage/core.config_entries) — a config-dir read also yields every webhook capability URL.
- Mobile apps: not source-read (bound). They consume the OAuth2 flow as normal refresh tokens (client_id = app URL) — server-side lifecycle = normal class above.
- Ingress (HAOS): Supervisor-issued session cookies, Supervisor repo not read (bound).
- Legacy: legacy_api_password http provider + trusted_networks provider still exist as opt-in auth providers (not default).
